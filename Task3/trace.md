# Архитектурное решение по трейсингу
## Мотивация:
Так как сейчас мы уже знаем проблему бизнеса: потеря заказов и их невыполнение в срок, нам критически важно отслеживать запросы, чтобы понять, на каком этапе они теряются.

## Предлагаемое решение:
1. Нам необходимо присваивать trace ID для каждого запроса.
2. Важно отслеживать: время старта запроса, время назначения запросу каждого статуса, ошибки. 
3. Отслеживаем 3 основные цепочки: 
   - API USER → MES (время приема, сколько занимает обработка, процент ошибок при расчете)
   - Customer → Shop → RabbitMQ → MES / CRM (соотношение сообщений в очереди с результатом в MES и CRM — так мы отследим потерянные заказы)
   - CRM → RabbitMQ → MES (доставляются ли сообщения, приходят ли менеджеру подтверждения о завершении производства)
4. Собираем данные с помощью OpenTelemetry, экспортируем в Prometheus и визуализируем в Grafana, чтобы все метрики были в одном месте. 
   
## Компромиссы:
1. Внедрение трейсинга требует доработки на стороне MES, но эта часть может потребовать привлечения дополнительного эксперта по C#. Поэтому на первом этапе трассировка MES может быть ограниченной.
2. Так как логировать все, включая тело запроса, мы не можем — это даст слишком большую нагрузку, то лучше использовать sampling (например, 10% от общего объёма). Это позволит собирать репрезентативную информацию без перегрузки системы.
3. Некоторые полезные данные могут считаться персональными или чувствительными. Нужно продумать систему безопасности для работы с трейсингом.

## Безопасность:
1. Все чувствительные данные, включая user_id, manager_id, model_id, должны быть либо анонимизированы, либо агрегированы на этапе экспорта трассировок.
2. Доступ к данным трейсинга предоставляется только авторизованным сотрудникам с ролью "Поддержка" или выше, через систему аутентификации и авторизации (например, интеграция с LDAP или IAM).
3. Данные не должны экспортироваться за пределы внутренней инфраструктуры, если иное не оговорено регламентом.
