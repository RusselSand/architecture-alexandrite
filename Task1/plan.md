# Планирование: анализ, идентификация проблем и поиск решений
## Существующие и потенциальные проблемные места
1. При загрузке моделей в S3 сейчас нет верификации и проверки количества полигонов, нет ограничений по объему файлов.
2. Внутренние клиенты и пользователи API имеют одинаковый приоритет.
3. RabbitMQ не лог, возможна потеря данных, нет идемпотентности.
4. Расчёт стоимости — это самая "тяжелая" часть архитектуры, она не должна быть совмещена ни с какими другими модулями.
5. Обработка заказов и загрузка 3D так же должны быть разделены, так как потенциально могут тормозить друг друга.
6. Только ручное тестирование тормозит разработку новых фич и выкладку обновлений.
7. Нет четких SLA — определяем проблемы по жалобам клиентов. 
8. Ручной релиз — также узкое место, лучше сделать какие-то пайплайны для автоматизации.
9. Приложение и БД имеет по одному инстансу, так что нет отказоустойчивости и масштабируемости.
10. БД содержит и еще не обработанные заказы, и старые заказы. Нет механизма архивации или удаления старых моделей.

## Инициативы для устранения нежелательных ситуаций
1. Выделение подсчета стоимости в отдельный сервис.
2. Выделение загрузки 3d моделей в отдельный сервис. Так как подсчет стоимости может занимать до получаса, и это самое узкое место системы, необходимо использовать Backpressure для регулирования его загрузки.
3. Реализовать автотесты для существующего кода и добавить их в процесс билда артефактов, чтобы мы как можно быстрее могли исправлять баги и выкатывать новые фичи.
4. Нанять специалиста по автотестам, чтобы быстрее перейти на новую схему тестирования.
5. Реализовать мониторинг с помощью Prometheus + Grafana, чтобы отслеживать сбои в системе и успевать на них реагировать раньше, чем получим отзывы клиентов.
6. Автоматизировать процесс релиза.
7. Добавить шардирование БД и реплики приложения для повышения отказоустойчивости.
8. Реализовать верификацию и проверку количества полигонов для загрузки модели (для пользователей API подумать над привязкой стоимости использования к количеству полигонов), добавить ограничения по объему файлов.
9.  Реализовать приоретизацию пользователей и использовать ее при регулировании загрузки модуля подсчета стоимости. Предложить варианты отложенной обработки для пользователей API (например, в дневное время наши клиенты получают расчет стоимости в режиме реального времени, а в ночное время модуль подсчета стоимости обрабатывает заявки со стороны пользователей API).
10. Потенциально перейти от распределенных очередей к распределенным логам или подумать над реализацией ретраев для повторной отправки сообщений, чтобы не терять события.
11. Создать механизм архивации старых заказов и их переноса в отдельное хранилище.
12. Для улучшения надежности RabbitMQ используем Durable Queues, Persistent Messages и Dead Letter Queues. Добавляем мониторинг и алерты для отслеживания перегрузки очереди и ошибок.

## Три главные инициативы на полгода
1. Выделение загрузки 3d моделей в отдельный сервис: это самое узкое место системы, которое должно использовать Backpressure для регулирования его загрузки, иначе мы так и будем терять заказы и клиентов.
2. Реализовать верификацию и проверку количества полигонов для загрузки модели: неограниченный ввод является угрозой всей системе.
3. Реализовать мониторинг с помощью Prometheus + Grafana, чтобы отслеживать сбои в системе и успевать на них реагировать раньше, чем получим отзывы клиентов: мы теряем слишком большое количество клиентов из-за того, что не реагируем вовремя.
